# UX 4-B3: 방문 예정일 (저장 구조 변경 PR, 운영 병합 보류)

기준: main `f00f132`(4-B1·4-B2 병합·배포 완료). 측정은 데모 빌드(가짜 데이터). 실제 사용자 시험·실제 계정 동기화 시험은 하지 않았다.

## 데이터 모델 조사 결과
- 프로젝트는 `project:<id>` 기록 하나(버전 1). 읽을 때 `clean()`이 알려진 칸만 골라 읽는다. 방문 기록은 `visitlog:<id>`로 따로 있고 `projectId`로만 연결된다.
- 계정 동기화(`sync.js`)는 프로젝트 객체를 칸을 고르지 않고 통째로 보내고 받는다. 그래서 새 선택 칸은 그대로 전달된다(시험으로 JSON 왕복 확인). 합칠 때 같은 ID가 다르면 사본(`-copy-`)으로 보관하는 기존 방식도 새 칸을 그대로 가져간다.
- 수정은 `updated` 값으로 오래된 화면의 저장을 거절한다(기존 `conflict`). 예정일 수정도 같은 경로를 쓴다.

## 설계
- 새 칸 `planned`(`YYYY-MM-DD` 또는 빈 값)를 **선택 항목**으로만 추가. **버전은 1 그대로**: 버전을 올리면 이전 화면 코드를 가진 기기에서 프로젝트가 통째로 사라진다(기존 시험 "지원하지 않는 버전은 건드리지 않음"과 같은 원리).
- 칸이 없는 기존 프로젝트는 예정일 없음으로 읽히고, **읽기만으로는 저장 내용이 바뀌지 않는다**(시험으로 확인). 깨진 값(`곧`)은 예정일 없음으로 읽고 프로젝트는 살린다.
- 새 날짜는 오늘 이후만 저장. 이미 저장된 지난 날짜는 다른 수정(이름·후보)이 지우지 않고, 비우기는 언제든 가능.
- 예정일(계획)과 방문 기록(실제)은 서로를 바꾸지 않는다. 화면에서 날짜로만 견줘 "예정일에 남긴 방문 기록 N건" 또는 "예정일이 지났어요, 다녀왔다면 방문 기록을 남겨 주세요"를 보여 준다.
- 날짜 입력은 브라우저 기본 날짜 입력(`type=date`)이고 새 라이브러리는 없다. 보관한 프로젝트에서는 상자를 숨긴다.

## 시험 (node 96 / pytest 280 통과, 새 시험 node 10 + pytest 1)
옛 프로젝트 읽기·무변경 / 설정·변경·취소 / 보관·복원·다른 수정 후 유지 / 잘못된 날짜·지난 날짜 거절 / 저장된 지난 날짜 유지·삭제 / 깨진 값 / 다른 기기의 오래된 저장 거절 / 저장 실패 시 원본 유지 / 비회원·계정 분리 / 계정 동기화·사본 JSON 왕복.
화면 시나리오(데모, 390폭): 옛 프로젝트 → 설정 → 변경 → 취소(후보 2곳 그대로), 다른 화면 갔다가 뒤로·새로고침 후 유지, 지난 예정일(기록 없음·있음), 깨진 값, 보관, 후보 0곳 프로젝트.

## 측정
- 프로젝트 화면 × 5폭 × 밝음/어둠 × 4상태 = 40건: 가로 넘침·오류·잘림·터치 작음 0. 화면 흔들림은 1280폭 3건(0.035~0.037)이 기준 0.02 초과 — 변경 전 main도 같은 화면에서 0.038(예정일 칸과 무관한 기존 이동). axe 0건.
- Lighthouse는 이번 PR에서 측정하지 않음(프로젝트 화면 한 구역 추가, 새 스크립트 없음).

## 해결하지 못한 것 / 병합 전 확인할 것
1. **두 기기가 동시에 예정일을 바꾸는 경우**: 한 기기 안에서는 오래된 화면의 저장을 거절하지만, 계정 동기화는 프로젝트를 통째로 최신 시각 쪽으로 덮는다(기존 동작). 예정일만 따로 합치지 않으므로 늦게 저장한 쪽이 이긴다. 실제 두 기기로 시험하지 않았다.
2. **실제 계정으로 동기화 시험은 하지 않음**(데모·가짜 저장소만).
3. 홈 "이어하기" 카드, 임장 코스 화면에는 예정일을 표시하지 않음. 방문 기록 입력 날짜를 예정일로 미리 채우는 연결도 하지 않음(예정일≠방문일 구분을 지키려고 날짜로 견주기만 함).
4. 알림은 없음(앱을 열어야 보임).
5. 이전 버전 코드를 가진 기기에서 이 프로젝트를 수정하면 `planned` 칸이 사라질 수 있다(옛 코드가 칸을 모름). 배포 직후 오래 열어 둔 화면이 이에 해당.
