# 일조 미리보기 4-D: 목적 중심 정리 + 입체(2.5D) 그림

명령서(Sun Preview UX 4-D)의 항목별 처리 기록. 사람이 직접 써 본 확인은 **하지 못했다**(자동 확인만).

## 1. 진단 (이전 화면, 데모 데이터 같은 단지·조건, `docs/ux4d/before/`)
| 항목 | 390폭 | 820폭 | 1280폭 |
|---|---|---|---|
| 결과 숫자('약 N시간') 위치(스크롤 y) | 1559 px (첫 화면 844 밖) | 1201 px | 1319 px |
| 결과 앞에 있는 누를 곳 | 39개 | 35개 | 42개 |
| 카드 수 | 10 | 10 | 10 |
| 문서 높이 | 6752 px | 4785 px | 4304 px |
- 입력 4칸(단지·동·층·날짜)이 결과보다 위에 길게 쌓였고, 동 13개 칩이 한 화면을 차지했다.
- 같은 내용이 세 곳에 나뉘어 있었다(결과 카드, 층별 그림, 평면도+시간 막대). 설명 문구가 카드마다 반복됐다.
- 색 의미: 노랑=직사광, 줄무늬=앞 동 가림, 점=벽 반대편(시간 막대) / 파랑·주황·줄무늬(평면도) / 남색~주황 5단계(층별)가 서로 달랐다.

## 2. 새 구조 (결론 먼저, 근거는 접음)
1) 조건(단지·동·층·날짜): 동은 한 줄로 접고 '바꾸기'로 펼침. 날짜는 세그먼트(동지/하지/오늘). 층은 -/슬라이더/+ 와 '8층 / 25층 (지상 약 22.6 m)' 표시.
2) 핵심 요약: 직사광 가능 시간(추정, 큰 글씨), 그 시간대, 앞 동에 가려지는 시간, 가장 크게 가리는 동, 가리는 동 N개 자세히(접힘).
3) 시간대 막대: 직사광 가능 / 앞 동에 가림 / 해가 벽 반대편 / 해가 없음 (색+무늬+글자 범례).
4) '왜 가려지나요?' 한 카드 안에 같은 조건을 보는 **세 가지 보기: 입체 · 평면 · 층별** (세그먼트). 기본은 입체.
5) 날짜별 비교, 6) 현장 확인(접힘), 7) 계산 근거·한계·출처(접힘, 출처 한 줄은 항상 보임).
- 기존 계산 코드(`shadow.js` 계산, `preview-calc.js`)와 15분 칸, 데이터 계약, 주소 상태(단지·동·층·날짜·시각·넓게 보기)는 그대로. 주소에 `v=iso|plan|floor` 하나만 추가.
- 근거 없는 '좋음/나쁨', 점수, 등급은 만들지 않았다.

## 3. 입체 그림 방식 선택 (비용 비교)
- 선택: **SVG 2.5D(등각 투영), 고정 시점**. 새 라이브러리 0개. 새 파일 `static/preview-iso.js` 12.6 KB(압축 4.9 KB).
- 비교 대상: three.js 최소 빌드 약 692 KB(압축 약 171 KB) + 건물 수백 개 메시/그림자 맵. 이 화면이 설명해야 하는 것은 '높이 관계와 해 쪽 선이 어느 동에 닿는가'뿐이라, 투영·가림 정확도가 SVG로 충분해 도입하지 않았다. 실제 3D는 나중에 필요가 입증될 때 별도 검토.
- WebGL을 쓰지 않으므로 '미지원 폴백'이 따로 필요 없다. 그래도 같은 내용을 **평면 보기**(기존 평면도)로 언제든 고를 수 있다. 움직임 효과(애니메이션)는 쓰지 않아 동작 줄이기 설정과 충돌하지 않는다.
- 그림 규칙: 내 동=브랜드 파랑, 하루 중 가리는 동=주황, 다른 건물=회색, 고른 층=노란 띠와 '8층 창' 표시, 해 쪽 선이 앞 동에 닿으면 빨간 ✕(닿지 않으면 점선+해 표시). 화면 밖 일반 건물은 그리지 않는다.

## 4. 계산과의 정합성 (자동 시험 `tests/test_preview_iso.cjs`)
- 입체 그림은 새로 판정하지 않는다. 해 쪽 선이 앞 동에 닿는지는 `shadow.js` 의 같은 식(`hitT`, `hOf`)으로 다시 구하고, **기존 계산이 '앞 동에 가림'이라고 한 칸과 100% 일치**하는지를 대전·세종·청주 3개 단지, 동 여러 개 x 3개 층 x 3개 날짜(동지·하지·오늘) x 모든 15분 칸(3천 칸 이상, 가림 300칸 이상)에서 확인했다. 가린 동은 계산 결과의 가림 목록 안에 있다.
- 그림자 방향·해 위치는 선택한 시각의 `sun()` 값을 그대로 쓴다. 그림자 모양은 `shadowPoly`(기존 평면도와 같은 것)를 땅 위에 올린 것이다.
- 한계(화면에도 적음): 건물 모양은 윤곽을 높이만큼 세운 단순한 상자라 실제 건물 모양이 아니다. 높이를 모르는 건물은 그리지 않는다. 지형·실제 창 방향(남쪽 긴 면 가정)·나무·담장·층별 구조는 반영하지 않는다. 그림자가 보여도 실내로 드는 햇빛과 같지 않다. 외부 자료와의 검증은 아직 없다.

## 5. 확인한 것 (자동)
- 동작(`docs/ux4d/behavior-check.mjs`, 17건 통과): 주소로 단지·동·층·날짜·시각 복원, 층 +/-·층별 그림 클릭·키보드 Enter·시각 슬라이더·+15분·날짜·동 바꾸기·입체 그림에서 동 누르기가 결과·슬라이더·주소와 동기, 시각을 10곳 바꿔 가며 입체 그림의 ✕/선 표시가 상태 문구와 항상 일치, 새로고침 복원, 평면·넓게 보기, 접힌 칸 펼치면 채워짐, 열려 있지 않은 단지 안내, 단지 없이 열기.
  - 이 확인으로 **새로고침하면 주소의 층이 기본값으로 덮어써지던 오류**를 찾아 고쳤다(이전 화면에도 있던 문제).
- 화면 점검: 라이트·다크 x 360/390/430/768/1280 x 입체/평면/층별 = 30조합, 가로 넘침·44 px 미만 누를 곳·14 px 미만 글자·스크립트 오류 0건.
- 접근성(axe, WCAG 2.1 AA): 라이트·다크 x 2개 폭 x 3개 보기 x 접힘/펼침 24조합 위반 0건. 다크에서 나온 글자 대비 문제(날짜 칩 보조 글자, 출처 꼬리표)를 고침. 그림은 `role=img` + 제목·설명, 층별 그림과 날짜·동·보기는 버튼(키보드 Tab/Enter).
- 화면 흔들림(CLS): 이전 0 / 이후 0 (입체·층별·단지 없음, 데모, 반복 3회). 라이트하우스에서 한 번 0.083이 나와(단지 고르기 칸이 아래로 이동하는 순서 문제) 고쳐서 0.
- 기존 시험: 브라우저 시험 6건(기존 `shadow` 11건 포함 별도 통과), 파이썬 4건 통과. 전체 시험은 PR 본문 참조.
