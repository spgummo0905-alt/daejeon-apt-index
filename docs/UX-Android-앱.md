# Android 앱(TWA) 사용감 개선 기록

**실제 APK/기기 시험은 하지 못했다(NOT_TESTED).** 이 컴퓨터에는 Android 기기, SDK, adb, Java가 없다. 아래 확인은 모두 *휴대폰 크기(360/390/430)와 Android 크롬 사용자 에이전트로 흉내 낸 브라우저*에서 한 것이며, APK 통과가 아니다. 운영 사이트 읽기(가로 밀림 재현)와 데모 사이트(수정 확인)로 나눠 적는다.

## 1. 구조 조사 (코드 사실)
- 앱 = `com.google.androidbrowserhelper.trusted.LauncherActivity`(TWA, androidbrowserhelper 2.5.0). 시작 주소 `https://www.jipgam.kr/index.html?skip=1`. 화면·기능은 웹과 같은 코드를 쓴다.
- `index.html?skip=1`은 저장된 마지막 지역(`dj-last-region`)이 있으면 그 지역으로 바로, 없으면 맨 앞 지역 선택(`/?skip=1`)으로 간다. 브라우저 `viewport`는 `width=device-width, initial-scale=1`(확대 차단 없음), 하단 탭은 이미 전역으로 있고(`.tabbar`, 720px 이하) 새로 만들지 않았다.
- TWA 설정에 있던 것: 상태바 색 `#182848`(어두운 남색), 하단바 흰색(고정). 다크 모드 값 없음. 시작 화면 배경 지정 없음.

## 2. 줌 문제를 종류별로 나눈 진단
| 종류 | 재현(브라우저 흉내) | 원인(코드) | 조치 |
|---|---|---|---|
| 핀치(두 손가락) 확대 | 막혀 있지 않음(의도) | viewport에 차단 없음 | **막지 않음**(접근성) |
| 더블탭 확대 | 코드상 가능(`touch-action` 기본값) | `html`에 지정 없음 | `html { touch-action: manipulation }` (더블탭 확대만 끄고 핀치·스크롤은 그대로) |
| 글자 자동 확대 | 가로로 돌릴 때 글자 크기가 달라질 수 있음 | `text-size-adjust` 지정 없음 | `100%` 고정(시스템 글자 크기 설정은 따름) |
| 가로 밀림 | **운영 단지 상세에서 재현**: 대전 트리풀시티5 등 4곳 중 3곳, 360/390/430 모두(문서 폭 422·437·458 > 화면) | ① 단지 정보 `.ki-note`가 `white-space: nowrap`이라 긴 안내(관리비·주차)가 칸 밖으로 ② 가격 표 영역 `.pc-tables`의 격자 칸이 표 폭만큼 늘어남(`1fr`=`minmax(auto,1fr)`) | `.ki-note`만 줄바꿈, `.pc-tables`를 `minmax(0,1fr)`로. 같은 4곳 x 3폭 12조합: 이전 9곳 넘침 → 이후 0. 데모 51쪽 x 폭 조합 넘침 0 |
| 지도·일조 영역 제스처 | 지도(카카오)는 자체 처리, 일조 SVG는 `touch-action: manipulation` | 전체 스크롤과 충돌 없음(SVG는 확대·드래그 제스처가 없음) | 변경 없음. 회전/확대를 넣을 때는 장면 안에서만 `touch-action`을 따로 지정 |

## 3. 앱답게 만든 것 (기존 하단 탭 재사용)
- `static/shell.js`(새, 2.3KB): ① 하단 탭으로 다른 화면에 갔다가 같은 탭으로 돌아오면 보던 위치로(탭에 막 도착했을 때만, 주소에 `#`가 있으면 하지 않음) ② 지금 있는 탭을 다시 누르면 맨 위로(앱의 흔한 동작, 새 화면으로 이동하지 않음) ③ 키보드가 올라오면(`visualViewport` 높이가 140px 이상 줄고 입력칸에 커서) 하단 탭을 숨겨 입력칸을 가리지 않게. 저장은 `sessionStorage`만(기록 저장소·계정 동기화는 건드리지 않음).
- 하단 탭 누르는 칸 최소 높이 48px.
- 하단 탭 4곳 `speculationrules` prefetch(moderate): 지원 안 하는 브라우저는 무시. **측정으로는 효과를 확인하지 못했다**(로컬 흉내에서 탭 이동 256 → 259 ms, 변화 없음. 실제 네트워크·실기기에서 확인 필요).
- 상태바·하단 시스템바 색: 밝게 `#F4F3EF`/`#FFFFFF`, 다크 `#111110`/`#1D1D1B`(사이트 바탕 변수와 같은 값), 시작 배경 `pageBg`. 웹 `theme-color`도 밝게/다크 따로. **APK를 다시 빌드해야 적용된다**(`android/**` 변경 → android 워크플로가 시험용 APK를 만든다).

## 5. 못 한 것 · 제약 (솔직하게)
- 실제 APK에서 Back 키, 앱 복귀, 딥링크, 로그인 복귀, 상태바·내비바 색, 키보드 가림은 **NOT_TESTED**. 재현 절차: 시험용 APK 설치 → ① 홈→찾기→단지→Back 3번 ② 홈 화면 이동 후 복귀 ③ 카카오 로그인 후 복귀 ④ 검색칸 눌러 키보드 열기 ⑤ 다크 모드 켜고 상태바·하단바 색 확인 ⑥ 단지 상세에서 가로로 밀어 보기.
- TWA 한계: 화면 전환 애니메이션, 하단 탭을 앱 고유 UI로 만드는 것, 시스템 Back 동작 재정의는 TWA 안에서 웹 쪽으로는 한계가 있다(크롬이 처리). 이를 넘으려면 네이티브 셸이 필요하다.
- P2 비교(TWA 유지 vs Kotlin/Compose 셸): 
  - **TWA 유지**: 개발·유지보수 최소(웹 한 벌), 배포 즉시 반영, 성능은 크롬 의존, 앱다운 전환·제스처는 웹으로 구현해야 하고 시스템 동작 제어에 한계.
  - **Compose 셸(WebView 포함 하이브리드)**: 하단 탭·전환·Back·푸시를 네이티브로 제어 가능, 하지만 WebView 별도 관리·키 관리·스토어 심사·두 벌 유지가 필요하고 웹 로그인(카카오)·서비스 워커 호환 점검이 크다. **승인 없이 전환하지 않음.** 지금은 TWA 유지가 비용 대비 합리적이라는 의견(실기기 시험 후 재평가).
