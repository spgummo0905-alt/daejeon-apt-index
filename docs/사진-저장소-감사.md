# 현장 사진 저장소 감사와 비공개 전환 절차

작성 기준: 2026-11-05. 운영에는 아무것도 적용하지 않았습니다. 이 문서는 확인한 사실, 위험, 적용 순서, 되돌리는 방법입니다.

## 1. 확인한 사실 (운영을 읽기만 해서 확인)

`python scripts/photos_audit.py <저장소 주소> <공개용 키>` 로 언제든 다시 확인할 수 있습니다. 사진 내용은 읽지 않습니다.

| 항목 | 결과 | 뜻 |
|---|---|---|
| `photos` 버킷 | **공개** (`public = true`) | 주소만 알면 로그인 없이 열림 |
| 로그인 없이 목록 요청 | 막힘(0건) | 둘러보며 찾을 수는 없음 |
| 올리기·지우기·목록 정책 | 본인 폴더(`<회원>/…`)만 | 남의 폴더에 쓸 수 없음 |
| 사진 주소 | `<회원 id>/<단지>/<무작위>.jpg` | 회원 id는 공유 화면에서 노출될 수 있음 |
| 옛 사진 이름의 무작위 부분 | 시각 + `Math.random` 6자(약 31비트) | 추측 난이도가 낮음 |
| 새 사진 이름 | 96비트 암호학적 난수 (이번 변경) | 추측 불가 |
| 개인정보처리방침 | "주소를 아는 사람만 볼 수 있어요" | 현재 구조와 일치 |

### 위험 평가
- 사진은 위치 정보를 지우고 1280px로 줄인 현장 사진입니다. 얼굴·번호판·세대 내부가 찍혔을 수 있습니다.
- 공개 버킷의 보호는 "주소를 모른다"뿐입니다. 주소가 메신저·브라우저 기록·공유 링크 화면에 남으면 그 뒤로는 막을 수 없고, 공유를 끊어도 사진 주소는 계속 열립니다.
- 계정을 삭제하면 사진도 지우도록 되어 있었지만, 사진 삭제 요청이 실패해도 계정이 먼저 지워질 수 있었습니다(공개 저장소에 주인 없는 사진이 남음). **이번에 고쳤습니다**: 사진 삭제가 실패하면 계정 삭제를 멈춥니다.

## 2. 이번에 코드로 반영한 것 (운영 데이터 영향 없음)

1. 계정 삭제가 사진을 먼저 확실히 지우고, 실패하면 멈춥니다. (시험으로 고정)
2. 새 사진 이름을 96비트 난수로 바꿨습니다. 옛 사진은 그대로입니다.
3. 본인 화면(현장 모드, 관심 화면, 인쇄)은 공개 주소가 안 열릴 때만 로그인 토큰으로 임시 주소(1시간)를 받아 한 번 다시 시도합니다. 지금은 공개 주소가 열리므로 동작이 바뀌지 않습니다. 비공개로 옮겨도 **본인 화면은 깨지지 않게** 미리 준비한 것입니다.
4. `scripts/supabase_setup.sql` 을 다시 실행해도 버킷이 공개로 되돌아가지 않게 했습니다.
5. 읽기 전용 감사 스크립트와 전환·되돌리기 SQL을 만들었습니다(`scripts/migrations/`). 아직 실행하지 않았습니다.

## 3. 비공개로 옮길 때 깨지는 것: 가족과 함께 보기

`share.html`(공유 링크)은 로그인하지 않은 가족이 봅니다. 버킷을 닫으면 **공유 화면의 사진이 안 열립니다.** 임시 주소는 소유자의 로그인이 있어야 만들 수 있기 때문입니다.

해결 후보 (아직 만들지 않음, 아래 순서로 검증 후 결정):

- **A. 공유 토큰으로 읽기 허용 (권장 검토)**: 저장소 읽기 정책에 "요청 머리말의 공유 토큰이 `shares` 표에 있고 그 주인의 폴더인 경우"를 추가하고, 공유 화면이 토큰을 머리말에 실어 임시 주소를 받습니다. 공유를 끊으면(`share_revoke`) 즉시 막힙니다. 장점: 현재 구조 유지, 별도 서버 불필요. 위험: 저장소 정책은 이 환경에서 시험할 수 없어 **운영과 같은 구성의 시험 프로젝트에서 먼저 확인**해야 합니다.
- **B. 공유 화면에서 사진 빼기**: 가장 안전하지만 기능 후퇴입니다.
- **C. Edge Function**: 토큰을 확인하고 임시 주소를 발급. 서버 코드가 늘어 이번 범위 밖입니다.

## 4. 적용 순서 (운영 변경은 5단계부터, 한 단계씩)

1. (완료) 이 코드 배포 → 본인 화면이 서명 주소 재시도를 갖춘 상태가 됨.
2. 공유 화면 방식(A 또는 B)을 시험 프로젝트에서 검증하고 코드 반영·배포. 이 단계 전에는 닫지 않습니다.
3. 적용 전 기준 기록: `python scripts/photos_audit.py …` 결과와 `select count(*) from storage.objects where bucket_id='photos'` 값을 적어 둡니다.
4. 운영 DB 백업 확인(Supabase 대시보드의 백업/Point-in-time). 사진 파일은 이 SQL이 건드리지 않지만 정책 변경 전 확인합니다.
5. `scripts/migrations/photos_private_apply.sql` 실행(트랜잭션, 버킷 한 줄만 바꿈). 사진 수가 같은지 확인하고 커밋.
6. 확인: 감사 스크립트가 종료 코드 0(비공개), 본인 화면에서 사진이 보임, 공유 화면에서 사진이 보임(2단계 방식대로), 옛 공개 주소는 열리지 않음.
7. 개인정보처리방침의 사진 문구를 "로그인한 본인, 공유 링크를 받은 사람만"으로 고칩니다.

## 5. 되돌리기

문제가 있으면 `scripts/migrations/photos_private_rollback.sql` 을 실행합니다(버킷을 다시 공개로). 파일은 이동·삭제하지 않으므로 데이터 손실이 없습니다. 되돌리면 옛 공개 주소가 즉시 다시 열립니다.

## 6. 남은 위험
- 옛 공개 주소가 이미 외부에 퍼졌다면 닫기 전까지 열립니다. 닫으면 막힙니다(주소를 바꾸지 않고도).
- 임시 주소(1시간)를 받은 화면을 캡처해 공유하면 1시간 동안 열립니다. 일반적인 서명 주소의 한계입니다.
- 사진 파일명 자체에 회원 id가 들어 있습니다. 이름을 바꾸는 이전은 이번에 하지 않았습니다(링크 깨짐 위험).
